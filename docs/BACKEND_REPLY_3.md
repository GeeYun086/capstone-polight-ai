## 0. 먼저 — 증권 분석 실패 (진행 중)

프론트 폴링이 `status=FAILED`, `failureReason=증권에서 보장 담보를 찾지 못했습니다.
에이전트 출력 형식을 확인하십시오.`를 받은 건입니다.

```
tripId      76359d7d-5063-4cbd-8fc7-99acc05bc1ae
documentId  d90d4252-805b-471f-8f37-a1d555778290
```

### 0-1. 백엔드·프론트 문제가 아닙니다

그 문구는 저희가 만든 문자열입니다(`analysis_service.py`). 추적 결과:

| 단계 | 판정 |
| --- | --- |
| 요청 스키마 | ✅ 통과 (422 아님, 잡 생성됨) |
| **presigned URL 다운로드** | ✅ **성공** — 실패했다면 다른 문구가 나갑니다 |
| Upstage 에이전트 잡 | ✅ `completed`로 종료, JSON 파싱까지 성공 |
| 담보 추출 | ❌ **여기서 0건** |
| 실패 콜백 왕복 | ✅ 정상 (사유가 프론트까지 도달한 것이 증거) |

즉 **연동 1·2단계는 이미 동작하고 있습니다.** 실패는 저희 내부, 에이전트 출력을
우리 스키마로 옮기는 한 단계에서 났습니다.

### 0-2. 남은 원인 후보는 둘입니다

저희 어댑터는 에이전트 출력의 `coverage_by_age_table` 키를 읽습니다. 이 키 이름은
실제 증권(한화손보) 1건을 보고 정한 것이고, 스키마는 코드가 아니라 Upstage Studio
에이전트에 저장돼 있습니다.

| 후보 | 내용 |
| --- | --- |
| ② | 검증한 것과 **다른 보험사·양식**의 증권. 에이전트가 표를 못 잡거나 다른 키로 냄 |
| ③ | 증권이 아닌 문서(약관 등)가 **증권 경로로 직행** |

① Studio 설정 변경도 배제하지 못하지만 순위를 내렸습니다. 저희 증권 코드는 8/17 이후
변경이 없고, **배포 환경에서 증권 경로가 성공한 기록이 없습니다.** 기존에 확인한
"담보 21건 / 금액 21/21"은 컨테이너 밖에서 로컬 mock 서버로 돌린 결과입니다. 이번이
실제 경로의 첫 실행이라, "되던 것이 깨진" 상황이 아닙니다.

### 0-3. 필요한 정보 (요청 1)

②와 ③을 가르려면 이것만 알려주시면 됩니다.

- `policy_documents.document_kind` 값 (위 `documentId` 기준)
- 그 문서의 **원본 파일명과 실제 페이지 수** (가능하면 파일 자체)

약관·영수증이 `CERTIFICATE`로 들어온 것이면 ③, 진짜 증권이면 ②이고 저희 어댑터
수정으로 갑니다. 저희 쪽에서는 Upstage Studio 콘솔에서 해당 잡의 출력 키를 직접
확인하고 있습니다.

### 0-4. 저희가 이번에 고친 것

원인 확정과 별개로, 같은 실패가 다시 나면 원인을 찾을 수 있도록 넷을 고쳤습니다.

| 내용 | 이유 |
| --- | --- |
| 에이전트 출력 **구조**를 로그에 남김 (키 이름·행 수만, 값은 제외) | 실패 시 남는 단서가 문구 하나뿐이었습니다 |
| 증권 경로에 **길이 컷** 적용 | 아래 2-2. 규격서와 어긋나 있던 유일한 지점입니다 |
| `CERTIFICATE`인데 페이지 수가 많으면 경고 + 실패 사유 분리 | 오분류가 "담보를 못 찾았다"로 위장됩니다 |
| **실패 사유를 사용자 문구와 내부 진단으로 분리** | 아래 1-7 |

값은 로그에도 남기지 않습니다. 증권에는 피보험자 이름·생년월일·증권번호가 들어 있어
키 이름과 개수까지가 안전한 경계입니다.

## 1. 09절 확인 요청 6건

| # | 항목 | 답 |
| --- | --- | --- |
| 1 | 10초 안에 응답되는지 | **예.** 202 즉시 응답 (1-1) |
| 2 | 콜백 재시도 정책 | **요청하신 대로 이미 구현됨** (1-2) |
| 3 | `sources[]` 지금부터 보낼지 | **이미 보내는 중** (1-3) |
| 4 | 보험기간 추출 가능 여부 | **확인 중** — 에이전트 스키마에 달림 (1-4) |
| 5 | AI 컨테이너 환경변수 | 2차 회신 1-9에 있음. **단 compose는 분리가 설계입니다** (3-1) |
| 6 | 벡터 거리 연산자 | 2차 회신 1-5에 있음. 코사인 `<=>` (1-6) |

### 1-1. 10초 — 문제 없습니다

`POST /internal/analysis`는 요청을 받으면 **즉시 202로 응답**하고 분석은
`BackgroundTasks`에서 계속 돕니다. 동기 처리가 아니므로 read 10초에 걸리지 않고,
같은 문서를 4번 분석하는 일도 없습니다.

증권 분석은 수십 초, 약관 분석은 4~5분 걸립니다. 둘 다 응답과 무관합니다.

### 1-2. 재시도 — 요청하신 정책이 이미 들어가 있습니다

```
최대 3회, 지수 백오프 (2초 -> 4초)
재시도 대상   408 429 500 502 503 504 + 연결 실패·타임아웃
즉시 중단     400 401 404  (재시도해도 같은 결과)
```

400·401·404를 즉시 중단하라는 지적과 정확히 일치합니다. 멱등 처리를 해주신 덕에
중복 전송도 안전합니다.

### 1-3. `sources[]` — 약관 경로에서 이미 보내고 있습니다

`chunkId` + `sourceRole` + `quoteText` 형태로, 담보 배열 안에 넣어 보냅니다.
`coverage_item_id`는 보내지 않습니다. `UNIQUE(coverage_item_id, policy_chunk_id,
source_role)` 위반을 막기 위해 전송 전에 (chunk, role) 기준으로 중복도 제거합니다.

지금은 `raw_result_json`에만 보관된다는 것을 확인했습니다. 구현 후 백필하실 때 그대로
쓰실 수 있습니다.

**증권 경로에는 `sources[]`가 없습니다.** 증권은 청킹하지 않아 참조할 `policy_chunks`
행이 없습니다. 화면 카드는 나가지만 근거 조항은 약관 쪽에서만 생깁니다.

### 1-4. 보험기간 — 에이전트 스키마 확인이 선행입니다

2차 회신 1-2와 같은 항목입니다. `policies`의 `start_date`/`end_date`가 `NOT NULL`인데
콜백에 보험기간이 없다는 지적은 맞습니다.

현재 저희가 증권에서 읽는 것은 담보명·금액·카테고리·설명·보험사·상품명뿐이고
**보험기간을 읽는 코드가 없습니다.** 에이전트가 뽑고 있는지부터 확인해야 합니다.

- 뽑고 있으면 → 콜백에 싣는 것은 코드 수정만
- 안 뽑고 있으면 → Studio에서 스키마 수정 + 에이전트 재검증이 선행

필드명은 `startDate` / `endDate`, 형식은 `YYYY-MM-DD`로 하겠습니다.
0번이 정리되면 같은 작업에서 함께 확인하겠습니다.

### 1-6. 벡터 거리 연산자 (재기재)

| 항목 | 값 |
| --- | --- |
| 임베딩 모델 | Upstage `embedding-passage`(색인) / `embedding-query`(질의) |
| 차원 | **1536** — DDL `vector(1536)`과 일치 |
| metric | **코사인**. pgvector `<=>` |
| SQL top-K | 32 (최종 8건 × 4배 후보) |
| threshold | 없음 |

인덱스 opclass는 `vector_cosine_ops`입니다. 다만 **지금 만들지 않기를 권합니다** —
검색이 항상 스코프로 먼저 좁혀져 후보가 약관 1건당 300건 안팎이라 전수 계산이 더
빠르고 정확합니다. 자세한 근거는 2차 회신 1-5에 있습니다.

### 1-7. 함께 정한 것 — `failureReason`을 사용자 문구로 바꿉니다

규격서에는 없지만 이번 실패에서 드러난 문제입니다. `errorMessage`가
`analysis_results.failure_reason`을 거쳐 프론트 화면까지 그대로 내려가는데, 저희가
내부 진단 문구를 실어 보내고 있었습니다.

```
바뀐 것
  이전   증권에서 보장 담보를 찾지 못했습니다. 에이전트 출력 형식을 확인하십시오.
  이후   증권에서 보장 내용을 찾지 못했습니다. 증권 원본 파일인지 확인해 주세요.
```

**presigned URL도 새고 있었습니다.** 다운로드 실패 시 예외 메시지에 서명이 붙은 주소가
통째로 들어가 `failure_reason`에 영구 저장되고 화면에도 떴습니다. 지금은 주소는 저희
로그에만 남고 콜백에는 실리지 않습니다.

**백엔드 코드는 그대로 두시면 됩니다.** 받은 문자열을 저장·전달하는 현재 동작이 맞고,
저희가 보내는 문구만 바뀝니다.

내부 사유를 DB에도 남기고 싶으시면 콜백에 필드를 하나 더 두는 것이 맞습니다. 지금은
계약을 바꾸지 않고 AI 로그 + `analysisResultId`로 잇는 것으로 두었습니다. 필요하시면
말씀해 주세요.

프론트에는 별도로 요청드릴 것이 있습니다 — **FAILED일 때 `failureReason`을 그대로
띄우지 말고 fallback 문구를 두는 편이 안전합니다.** 저희가 문구를 미처 바꾸지 못한
경로가 남아 있을 수 있습니다.

## 2. 규격서를 코드와 대조한 결과

### 2-1. 이미 맞는 것 (수정 없음)

| 항목 | 저희 쪽 |
| --- | --- |
| 콜백 경로 2개 | 문자열까지 일치 |
| 204 응답 | 2xx 통과 처리 |
| `X-Internal-Api-Key`, 양방향 동일 키 | 일치. `SPRING_BASE_URL`이 있는데 키가 없으면 **기동 실패**로 두었습니다 |
| enum 4종 (`clause_type`·`source_content_type`·`coverageStatus`·`severity`) | 허용값 표로 관리. 모르는 값은 안전한 fallback |
| `policy_chunks.created_at`·`updated_at` DEFAULT 없음 | 직접 채웁니다 |
| `isCovered`·`sortOrder` 미전송 | 의도적으로 제외. 배열은 화면 표시 순서(중요도)로 정렬해 보냅니다 |
| `policyId` 제거 | 저희 스키마에서 optional이라 안 보내셔도 무해합니다 |
| 저장 순서 (`policy_chunks` INSERT → 콜백) | 지킵니다 |

### 2-2. 어긋나 있던 것 — 증권 경로의 길이 컷 (수정 완료)

약관 경로에는 규격서와 같은 값으로 길이 컷이 들어 있었는데, **증권 경로가 빠져
있었습니다.** 증권 쪽이 더 위험합니다 — 이 값들은 에이전트가 뽑은 문자열이라 길이를
저희가 통제하지 못합니다. 특히 `limitLabel`(100자)에 금액 원문이 그대로 들어갑니다.

터졌을 때의 경로가 나쁩니다.

```
limitLabel 101자
  -> 백엔드 500 (길이 검증 전이라 DB 제약 위반)
  -> 500은 재시도 대상이라 3회 모두 500
  -> 콜백 포기. 저희는 로그만 남김
  -> analysis_results.status = PROCESSING 영구 고착
  -> UNIQUE(document_id)로 재분석도 불가
```

분석은 성공했는데 화면은 영원히 로딩이고 에러도 뜨지 않습니다. **"길이는 Python 쪽에서
잘라 보내 주세요"를 그대로 받아, 두 경로가 같은 표를 쓰도록 한 곳으로 모았습니다.**

그쪽에서 400으로 바꾸는 개선을 후속 과제로 잡아두셨다고 했는데, 그때까지는 저희가
자릅니다. 400이 되면 원인 파악이 훨씬 빨라지니 넣어주시면 좋겠습니다.

### 2-3. 아직 안 보내는 필드 2개 (무해)

| 필드 | 현재 | 계획 |
| --- | --- | --- |
| `coveragesComplete` | 미전송 → `false`로 처리됨 | 필드를 추가하되 **값은 당분간 `false`** |
| `accuracyScore` | 미전송 (nullable) | 근거 없는 값을 넣지 않으려 비워둡니다 |

`coveragesComplete`를 바로 `true`로 못 보내는 이유는 2차 회신 1-3에 적은 그대로입니다.
**원본 표에 몇 줄이 있었는지를 에이전트가 알려주지 않습니다.** 이 상태에서 `true`를
보내면 근거 없는 값이 되고, 지적하신 "파싱이 빠뜨린 담보를 미가입이라고 답하는" 사고가
그대로 납니다. 에이전트가 행 수를 함께 내보내도록 고친 뒤 값만 켜겠습니다. 그 시점에
백엔드 코드는 바뀌지 않습니다.

### 2-4. 확인한 제약 — 문서 1건당 분석 1회

`analysis_results`에 `UNIQUE (document_id)`가 있어 재분석이 안 된다는 것, 그리고
`coverage_item_sources`가 청크를 FK 참조해 청크 DELETE가 위험하다는 것 확인했습니다.

**그래서 이번 실패 건(`d90d4252-…`)은 재시도할 수 없습니다.** 저희 수정을 검증할 때는
같은 파일을 **새로 업로드**해 새 `documentId`로 받아야 합니다. 재분석 API를 만드실
계획이 잡히면 알려주세요 — 청크 정리 순서는 저희 쪽에서도 준비할 것이 있습니다.

`STORAGE_TYPE=local`이면 AI 호출 클라이언트 빈이 등록되지 않는다는 것도 확인했습니다.
전체 흐름 확인은 `s3`로 하겠습니다.

## 3. 2차 회신이 반영되지 않은 것 같습니다

규격서 09절의 5·6번은 저희 2차 회신(`docs/BACKEND_REPLY_2.md`) 1-9·1-5가 이미 답한
항목입니다. 전달이 안 됐거나 반영 전에 작성된 것으로 보여, 그중 **작업 방향이 달라지는
것 하나**만 다시 적습니다.

### 3-1. `docker-compose.prod.yml`에 ai 서비스를 추가하지 마셔도 됩니다

09절 5번에 "`docker-compose.prod.yml`에 ai 서비스 블록을 추가해야 합니다"라고
적으셨는데, **저희가 파일을 빠뜨린 것이 아니라 일부러 분리했습니다.**

같은 compose에 넣으면 **Spring을 배포할 때마다 AI 컨테이너가 함께 재시작됩니다.**
분석은 응답을 보낸 뒤에도 프로세스 안에서 3~5분 더 돕니다(`BackgroundTasks`). 그 사이
재시작되면 작업이 통째로 사라지고 콜백을 못 보내 `analysis_results`가 `PROCESSING`에
고착됩니다. **에러도 로그도 남지 않습니다** — 지금 논의 중인 실패보다 더 조용한
고장입니다.

`docker network`만 공유하면 컨테이너끼리 이름으로 통신하면서 배포는 서로 독립적입니다.
AI 컨테이너는 이미 `polight_polight-network`에 합류해 있고, Spring 컨테이너에서
`http://polight-ai:8000/health`가 200으로 확인된 상태입니다.

백엔드가 `docker compose down`을 하면 저희 컨테이너가 붙어 있어 네트워크 삭제에
실패했다는 경고가 뜹니다. 무해합니다.

### 3-2. `SPRING_BASE_URL` 표기 — 확인했습니다

규격서에 `http://backend:8080`(운영)으로 적어주신 것을 표준으로 받겠습니다. 저희는
현재 `http://polight-backend:8080`으로 두었는데 같은 컨테이너로 해석됩니다. 표기를
맞추겠습니다.

경로를 하드코딩하라는 것도 확인했습니다. 저희 쪽 기본값이 규격서와 같은 문자열입니다.

### 3-3. 아직 답을 못 받은 5건 (2차 회신 3절)

| # | 내용 | 없으면 |
| --- | --- | --- |
| 1 | `/internal/terms/source` MVP 포함 여부 | 착수 시점을 정할 수 없음 |
| 2 | **`rag_service` 계정에 `policy_terms` INSERT 권한** | 약관 8건 이관 불가 |
| 3 | 약관 원문 S3 업로드용 presigned PUT | `stored_file_path`를 채울 수 없음 |
| 4 | `policy_chunks`에 `document_id` 단독 인덱스 | 스코프 필터가 인덱스를 못 씀 |
| 5 | `INTERNAL_API_KEY` 로테이션 시점 | 현재 값 유지 |

**2번이 챗봇 블로커입니다.** 규격서 06절에 "콜백이 도착하지 않으면 청크는 DB에 있는데
검색 결과가 0건"이라고 쓰신 것과 같은 종류의 문제가 지금 있습니다. 현재 공용 약관 청크
2225건은 `user_id`·`trip_id`·`documentId`가 모두 비어 있는데, `RagQueryRequest.tripId`가
필수라 저희 스코프 필터가 전부 걸러냅니다.

```
청크 2225건에 스코프 필터를 걸어본 결과
  scope 없음 (평가 스크립트 경로)     2225건 통과
  tripId만 (실제 요청 형태)              0건
  documentId까지 (실제 요청 형태)        0건
```

결과가 0건이면 정해진 문구로 답하므로 **에러도 로그도 남지 않습니다.** `rag/query`를
붙였는데 계속 "약관에서 확인할 수 없습니다"만 나온다면 이것 때문이니, 연동 문제로
오해하지 않으시도록 다시 적어둡니다. `policy_terms` 이관이 끝나면 `termsId` 스코프로
검색되어 해결됩니다.

## 4. `documentKind` 기본값 — 순서가 필요합니다

0-2의 후보 ③과 직접 관련된 항목입니다.

확인한 사실:

- 프론트가 업로드 시 `documentKind`를 **보내지 않습니다**
- 백엔드 기본값이 `CERTIFICATE`입니다
- 저희는 `documentType`이 오면 **그것을 신뢰**하고 페이지 수 안전망을 건너뜁니다
  (규격서에 "페이지 수로 추측하지 않도록 명시해 보냅니다"라고 하신 대로입니다)

그래서 사용자가 무엇을 올려도 증권 파이프라인으로 갑니다. 지금은 운영에서 들어오는
것이 증권뿐이라 실질 피해가 없지만, **사용자 약관 업로드 경로를 켜는 순간 전부 이
실패로 떨어집니다.**

기본값으로 방향이 정해지는 구조 자체를 없애는 것이 맞다고 봅니다. 순서가 있습니다.

1. **프론트가 `documentKind`를 명시해 전송** (증권/약관 업로드 화면 구분)
2. 그 배포가 끝난 뒤 **백엔드가 기본값을 없애고 필수 필드로**

뒤집으면 프론트 배포 전까지 업로드가 전부 400이 됩니다.

저희 쪽에서는 **선언된 타입을 뒤집지 않습니다.** 명시해 보내주신 값을 저희가 무시하면
어느 쪽이 맞는지 아무도 모르는 상태가 됩니다. 대신 `CERTIFICATE`인데 페이지 수가
30을 넘으면 경고를 남기고, 담보를 못 찾았을 때 실패 사유를 "증권이 아닌 문서로
보입니다"로 돌립니다. 실측 증권은 1~2페이지, 약관은 126페이지라 그 사이 어디에도 없는
값입니다.
