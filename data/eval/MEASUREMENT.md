# 측정 프로토콜 — 약관 기반 vs 증권 기반

증권 기반으로 전환하기 전후를 수치로 비교하기 위한 절차다.
"좋아진 것 같다"가 아니라 "무엇이 얼마나 좋아졌다"를 말하기 위한 것이고,
그 수치가 방어 가능하려면 아래 규칙을 지켜야 한다.

## 왜 4개 층으로 나누는가

한 덩어리로 "정확도"를 재면 원인 분리가 안 된다. 증권 전환은 카드 생성 방식,
약관 처리 시점, 검색 필터를 동시에 바꾸기 때문에, 수치가 올라가도 무엇 덕분인지
말할 수 없다. 그래서 층마다 따로 잰다.

| 층 | 무엇을 재나 | 도구 | 정답 |
|---|---|---|---|
| A. 보장 카드 | 증권 담보를 맞게 뽑았나 | `eval_coverage_cards.py` | `certificate_gold.json` |
| B. 라벨링 | 약관 조각에 카테고리가 맞게 붙었나 | `eval_labels.py` | `label_gold.csv` |
| C. 검색 | 질문에 맞는 조각을 찾아오나 | `eval_retrieval.py` | `questions.json` |
| D. 비용·시간 | 얼마나 빠르고 싼가 | 스톱워치 + 호출 수 | 불필요 |

## 지켜야 할 3원칙

**1. 정답을 먼저 고정하고 나서 측정한다.**
결과를 보고 정답을 고치면 그 수치는 아무것도 증명하지 못한다.
정답 파일을 채운 즉시 커밋해서 시점을 남긴다.

**2. 한 번에 하나씩 바꾼다.**
라벨링 개선과 증권 전환을 동시에 하면 어느 쪽 기여인지 말할 수 없다.
`eval_retrieval.py --no-mmr` 같은 토글이 있는 것이 이 목적이다.

**3. 측정을 스크립트로 남긴다.**
손으로 센 숫자는 재현되지 않는다. 모든 도구에 `--out`이 있으니 JSON으로 저장한다.
저장 파일에는 git 커밋이 함께 남아 어떤 코드로 낸 수치인지 추적된다.

## A. 보장 카드

### 정답 만들기

```bash
cp data/eval/certificate_gold.example.json data/eval/certificate_gold.json
```

**증권의 보장내용 표에 인쇄된 것만 옮겨 적는다. 약관을 보고 채우지 않는다.**
증권은 표라서 채점자가 누구든 같은 정답이 나온다. 이게 이 측정의 객관성을 담보하는
유일한 근거다. 약관을 정답 근거로 쓰면 "이 조항이 이 담보에 해당하는가"를 사람이
판단해야 하고, 그 순간 주관이 섞여 수치를 방어할 수 없게 된다.

표본은 증권 5~10장. 보험사가 겹치지 않게 고른다.
실제 증권이면 이름·증권번호는 지우고 저장한다.

### 측정

예측 결과를 `{certificate_id}.json`으로 저장한 디렉터리를 넘긴다.

```bash
python scripts/eval_coverage_cards.py --payload-dir data/eval/pred_terms --out data/eval/cards_terms.json --note "약관 기반"
```

```bash
python scripts/eval_coverage_cards.py --payload-dir data/eval/pred_cert --out data/eval/cards_cert.json --note "증권 기반"
```

### 지표

| 지표 | 무엇을 보나 |
|---|---|
| 담보 Recall | 빠뜨린 담보 |
| 담보 Precision | **지어낸 담보(환각)** |
| `limitAmount` 정확도 | 화면 금액의 신뢰도 |
| `coverageStatus` 정확도 | 가입 여부 판정 |
| `limitLabel` 충족률 | 화면 한도 칸 빈칸 노출 |
| 오염 필드 | `"null"` 같은 문자열이 화면에 새는 건수 |
| 인용 환각률 | `quoteText`가 약관 원문에 실제로 있는가 |

### ⚠️ 해석 주의

**약관 기반은 `limitAmount`에서 구조적으로 진다.** 약관 원문에 숫자가 아예 없기
때문이다("보험가입금액을 한도로"). 개인 계약 조건은 약관이 아니라 증권에 있다.

이건 불공정한 비교가 아니라 **측정의 요점**이다. 모델 성능 차이가 아니라 정보원의
차이를 보여주는 수치이므로, 발표에서는 이렇게 프레이밍한다:
"같은 LLM으로도 약관에서는 뽑을 수 없는 정보가 있고, 그것이 증권에는 있다."

`coverageStatus`도 마찬가지다. 약관은 그 상품이 팔 수 있는 모든 특약을 싣고 있어
사용자가 실제로 가입한 것이 무엇인지 알 방법이 없다.

## B. 라벨링

증권 카테고리로 약관을 좁혀 검색하는 계획이 이 라벨에 의존한다.
라벨이 틀려 있으면 필터를 켜는 순간 검색 품질이 지금보다 나빠진다.

### 정답 만들기

```bash
python scripts/make_label_sample.py
```

`data/eval/label_gold.csv`가 생긴다. `gold_category` 열만 채우면 된다.

- 무작위 추출(시드 42 고정). 눈에 띄는 것만 고르면 편향된다
- **자동 라벨은 일부러 넣지 않았다.** 보여주면 사람이 그것에 끌려간다(앵커링).
  채점할 때 `chunk_id`로 붙인다
- 판단 기준: "이 조각이 그 담보를 **설명하는** 조항인가". 다른 얘기를 하다가 단어만
  스친 경우는 `null`

### 측정

```bash
python scripts/eval_labels.py --out data/eval/labels_before.json --note "개선 전"
```

라벨링 로직을 고치고 청크를 다시 만든 뒤:

```bash
python scripts/eval_labels.py --out data/eval/labels_after.json --note "제목기준+상속"
```

### 지표

두 실패를 나눠서 본다. 원인도 고치는 방법도 다르다.

| 지표 | 뜻 | 고치는 법 |
|---|---|---|
| 과잉 라벨(over) | 정답 `null`인데 라벨이 붙음 | 제목 기준 매칭 |
| 누락 라벨(under) | 정답 있는데 `null` | 상속, 임베딩 분류 |
| 오분류 | 다른 카테고리로 붙음 | 매핑 키워드 정리 |

## C. 검색

baseline은 이미 고정되어 있다: `data/eval/baseline_2026-08-15.json`

```
Recall@1 64.0%  Recall@3 76.0%  Recall@5 84.0%  Recall@8 88.0%  MRR 0.7170
고유 조항 84% / 반복 조항 100%
약관 어투 100% / 일상 표현 80%
멀티턴 33%   ← 가장 약한 지점
```

같은 명령으로 다시 돌려 비교한다.

```bash
python scripts/eval_retrieval.py --out data/eval/retrieval_after.json --note "카테고리 필터 적용"
```

카테고리 필터를 켠 버전과 끈 버전을 각각 재면 필터의 기여를 단독으로 잴 수 있다.

## D. 비용·시간

가장 이견이 없는 수치다.

| 항목 | 측정 방법 |
|---|---|
| 사용자 대기 시간 | 요청 → 응답 스톱워치 |
| LLM 호출 수 | 약관 기반 7회(카테고리당 1회) vs 증권 기반 0회 |
| Upstage 페이지 과금 | 사용자마다 126p vs 상품당 1회 126p + 사용자당 2p |

`extract_all`의 카테고리당 6.32초는 `extraction_comparison.json`에 이미 측정되어 있다.

**N명이 같은 보험사 상품을 쓸 때 비용이 어떻게 나뉘는지**를 그래프로 그리면
사전 배치 구조의 이점이 한눈에 보인다.
